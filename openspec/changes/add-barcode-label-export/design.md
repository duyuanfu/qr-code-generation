## Context

用户要的是**商品条码标签**：贴在实物上、用**激光扫码枪**读、按毫米打印。这三点决定了它与现有二维码功能几乎没有可复用的算法部分，只有基础设施（订单/支付/上传/静态文件服务）能复用。

已核实的技术事实：

| 事实 | 依据 |
|---|---|
| 后端有全套一维码 writer | `core-3.5.3.jar` 内含 `Code128` `Code39` `Code93` `CodaBar` `EAN8` `EAN13` `UPCA` `UPCE` `ITF` `PDF417` 的 `*Writer.class`（上一轮做 GIF 时引入的依赖，白捡） |
| **前端没有任何一维码 writer** | `@zxing/library@0.21.3` 的 writer 只有 `QRCodeWriter` / `DataMatrixWriter` / `AztecWriter`；前端要出一维码必须新引 `jsbarcode`(~40KB) 或 `bwip-js`(~700KB) |
| 静态二维码是纯前端渲染 | `qr-code-styling` 在浏览器算，产物不经过后端；付费墙卡在「导出」 |
| 全站没有物理尺寸/DPI 概念 | 搜 `dpi` / `毫米` / `打印` 仅命中示例字符串 |
| 订单已有 `result_url` | 上一轮 GIF 变更加的 `orders.result_url`，正好用来做幂等 |

**核心矛盾**：本产品的价值主张是「二维码美化」，而一维码**几乎没有美化空间**——条的宽度比例由标准锁死，任何圆角、渐变、Logo 都会直接让激光枪读不出来。用户自己也清楚这点，明确要求「不加各种样式修改，能用就行」。

所以本次不做"更漂亮的条形码"，做的是**「能打印、能被扫码枪读到的标签」**。产品价值从"好看"换成"准"。

## Goals / Non-Goals

**Goals:**

- 输入一串商品编码，选出**物理尺寸正确的**标签：宽多少毫米、每模块多少毫米、放大倍率多少，全部明确可查。
- 打出来**激光枪能读**：静区完整、条宽为整数像素、对比度为纯黑白。
- EAN/UPC 的校验位**自动补全**；用户填错时直接指出正确值，而不是给一张错码。
- 交付前**自己先解一遍**，解不出就不核销、不交付。
- 计费方式与现有功能一致（下单 → 支付 → 携带 orderId 核销），¥2 单次。
- 预览免费且即时，但**天然不可打印**，不需要水印、不牺牲可读性。

**Non-Goals:**

- ❌ **不做样式美化**：不给条色/底色选择器、不做渐变/圆角/Logo。反相（浅条深底）在激光枪上基本读不出，这类"美化"是在制造废品。
- ❌ **不做批量生成**、不做 A4 拼版、不做标签纸套打（用户明确排除）。
- ❌ **不做 2D 码**（DataMatrix / PDF417 / Aztec）。虽然 ZXing 都支持，但那是另一个产品形态（工业零件、证件），且校验逻辑不同，留作后续独立变更。
- ❌ **不做 ITF-14 箱码 / GS1-128（带 AI 的 Code128）**。这两者需要 Application Identifier 解析（`(01)12345678901231(3103)000123`），是物流专用语义，混进来会让输入框变成"要么填数字要么填括号表达式"，把简单功能做复杂。
- ❌ 不做动态活码（条形码内容直接编码，没有短码与落地页）。
- ❌ 不做 Codabar / Code 93 / MSI 等长尾码制。

## Decisions

### D1. 编码放后端，前端不引新依赖

| 方案 | 依赖成本 | 打印尺寸精度 | 付费墙 | 结论 |
|---|---|---|---|---|
| 前端 `jsbarcode` | +40KB（gzip 后 ~15KB） | 一般（输出 canvas，DPI 靠 `scale` 猜） | 仍要前端拦截，可被截图 | 否 |
| 前端 `bwip-js` | +700KB（全码制含字体） | 好 | 同上 | 否 |
| 后端 ZXing | **0** | 完全可控（先定模块像素再反算毫米） | 服务端不返回就没有 | **采用** |

代价是打破"静态码纯前端算力"这条既有架构线。但这个代价换来三个真收益：

1. 零新依赖，包体积不动；
2. 物理尺寸能算准（前端 canvas 缩放会引入半像素，条宽比例立刻失真）；
3. 付费墙变干净——**未付费就不存在那批像素**，不用再玩"给未解锁用户画演示内容"的把戏（那个技巧在二维码上是必要的，因为像素一旦在浏览器里画出来就能截图）。

### D2. 码制只做 5 个，EAN-13 默认

| 码制 | 内容位数 | 校验位 | 典型场景 | 静区（每侧） | X 尺寸基准 |
|---|---|---|---|---|---|
| **EAN-13** | 12 位数字，第 13 位自动算 | GS1 mod-10 | 国内零售商品（69 开头）、店内码（20~29） | 11 模块 | 0.330mm |
| EAN-8 | 7 位数字，第 8 位自动算 | GS1 mod-10 | 小包装（口香糖、笔芯） | 7 模块 | 0.330mm |
| UPC-A | 11 位数字，第 12 位自动算 | GS1 mod-10 | 出口北美 | 9 模块 | 0.330mm |
| Code 128 | 1~48 个 ASCII | 自动（mod-103） | 内部 SKU、快递单号、序列号 | 10X | 0.250~0.500mm |
| Code 39 | 1~43 个 `0-9A-Z-. $/+%` | 无 | 工业资产牌、旧系统兼容 | 10X | 0.250~0.500mm |

**不强制 EAN-13 以 69 开头**：20~29 是合法的店内码（生鲜称重、自制品），强行拒绝会让一半用户没法用。只校验校验位。

Code 128 的子集（A/B/C）由 ZXing 自动挑选——纯数字会自动走 C 子集，长度直接减半。UI 上说明一句即可，不做手动切换。

### D3. 物理尺寸：以「整数模块像素」为准，毫米是结果

**这是整个功能最容易做错、也最影响成败的一步。**

一维码的条宽是模块宽的整数倍（EAN-13 是 1/2/3/4 模块四种宽度）。如果先定"标签 40mm 宽"再整体缩放图片，缩放系数几乎必然不是整数，四种条宽会被取整成不等比例——**激光枪按边沿间距判宽度，比例错了直接判废**，而且人眼完全看不出问题。

正确顺序：

```
用户输入：标签宽 W(mm)、DPI
    │
    ├─ 可用像素  availPx = round(W / 25.4 * DPI)
    ├─ 总模块数  modules = 符号模块数 + 2 × 静区模块数
    ├─ 模块像素  modulePx = floor(availPx / modules)      ← 唯一真正的自变量
    │
    ├─ 实际 X    xMm = modulePx / DPI * 25.4
    ├─ 实际宽    outMm = modules * xMm
    ├─ 放大倍率  mag = xMm / 0.330
    │
    └─ 校验：mag ∈ [80%, 200%]，否则拒绝并给出可用的尺寸区间
```

出图时把 `modulePx` 直接交给 ZXing 的 `MultiFormatWriter.encode(..., width = modules * modulePx, ...)`，它内部按整数倍渲染（`OneDimensionalCodeWriter.renderResult` 会算 `multiple`），**不会产生半像素**。这是这条链路能成立的根本原因。

实际感受一下取整的幅度（EAN-13，117 模块含静区）：

| DPI | `modulePx` | 实际 X | 放大倍率 | 成品宽 |
|---|---|---|---|---|
| 203（热敏） | 3 | 0.375mm | 113.7% | 43.9mm |
| 300（激光） | 4 | 0.339mm | 102.6% | 39.6mm |
| 600 | 8 | 0.339mm | 102.6% | 79.2mm |

203dpi 下 100% 需要 2.64px，取整到 3px 就偏了 13.7%——**在允许区间内**，但必须把这个数字显示给用户看，否则他会奇怪"我明明填了 40mm 怎么打出来 44mm"。

### D4. 静区是强制项，不是留白

EAN-13 标准要求左侧 11 模块、右侧 7 模块的静区。本次统一按**每侧 11 模块**（`EncodeHintType.MARGIN`），比两侧要求都宽，成本可以忽略。

三条硬规则写死在代码里，不给开关：

1. 输出图四周的静区**不得裁切**（用户想要"贴边省纸"时必须拒绝并解释）；
2. 条色恒为 `#000000`、底恒为 `#FFFFFF`，不提供配色（相对亮度对比度 21:1，是能保证激光枪读到的最稳妥取值）；
3. 标签底色区域必须是纯白，**不允许透明背景**——PNG 透明区在打印时常常变成打印机的"无墨"，落到牛皮纸/彩色纸上是灰底，对比度直接崩。

### D5. 人眼可读数字（HRI）自己画

ZXing 只出条，不出字。但商品标签没有数字就是废的——收银员要核对、理货要盘。

- 字体用 JDK 逻辑字体 `Monospaced`（只画数字与 ASCII，**不需要**中文，所以不必像 GIF 那样打包 Noto）。
- 位置固定在条下方居中，字号按标签高度自适应（约条高的 18%）。
- 严格 EAN 标准是 `1 + 6 + 6` 分组、首位落在左侧静区外、guard bar 向下延伸 5 模块。**本次不实现这套排布**，统一渲染成一行数字。理由：分组排布对人眼核对的增益很小，而实现它要拆字逐个定位，容易在窄标签上溢出。属于"能用"与"完美"之间的取舍，写在这里备案。
- 可选一行备注（商品名 / SKU），默认关闭，超长截断。

### D6. 免费预览 = 每模块 1 像素

预览要同时满足两个要求：**看得出对不对** 和 **无法拿去打印**。

- 每模块 1 像素（EAN-13 约 117×35px），前端用 `image-rendering: pixelated` 放大 3~4 倍显示。条边缘仍是硬边、结构完全真实，所以码制选错、内容填错一眼可见。
- 117px 宽印在 40mm 上只有 74dpi，**任何打印结果都是糊的**——付费墙自然生效，不需要水印。
- 加水位会破坏条码本身（水印压条 = 故意做成废码），既伤体验又要解释，不如从分辨率下手。

预览**不落盘**：直接返回 `data:image/png;base64,...`（约 1~2KB），避免每次调参都在磁盘上留垃圾，也不需要清理任务。

### D7. 导出交付 PNG + SVG 两份

- **PNG**：按用户选的 DPI（203 / 300）与整数模块像素渲染，用于直接打印。
- **SVG**：以 `mm` 为单位、`viewBox` 以模块为坐标，条用**游程合并的 `<rect>`**（一行连续黑模块合成一个矩形）而不是每模块一个，文件只有几 KB。印刷店/设计软件拿去做任意尺寸排版都不失真。一维码所有行的条完全相同（只有 guard bar 高度不同），所以 SVG 只需两组矩形。

两者都落在 `{uploadDir}/barcode/{orderId}.png|.svg`，对外 `/uploads/barcode/...`。

### D8. 计费：独立计费项 `barcode_export`，¥2/次

与 `static_export`（也是 ¥2）**同价但不同键**。理由：

- 后台"价格配置"面板按 `action_type` 分组，混用同一个键会让两类导出在统计里无法区分；
- 以后想单独调价（比如商品标签涨到 ¥3）时不用写迁移。

字段：`price = 2.00`、`valid_months = 0`（无服务期）、`per_item = 0`（一次性）、`sort_order = 960`。`INSERT IGNORE` 迁移，不覆盖管理员改过的价格。

订单语义完全复用 GIF 那套：`result_url` 非空即幂等；只有「文件已落盘 + 解码回验通过」才置 `used`；失败保持 `paid` 可重试。

### D9. 交付前解码回验，两档

自己生成的图自己解，本身是个弱测试（几乎必过），所以加一档**模拟劣化**：

| 档位 | 处理 | 模拟什么 |
|---|---|---|
| native | 原图直接解 | 理想扫描 |
| degraded | 缩放到 50% + 1px 高斯模糊后再解 | 打印偏移、塑封反光、扫描枪距 20cm |

两档都解出**且内容与请求一致、格式与请求一致**才算通过。不过就 422 + 原因，不核销。

这一档劣化校验还能顺带拦住一类真实错误：标签尺寸太窄导致 `modulePx` 过小（1~2px），native 能过、degraded 必挂——正好对应"印出来读不出"。

## API 契约

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| POST | `/api/barcode/preview` | 匿名 | 返回 `{ dataUrl, metrics }`；`modulePx` 恒为 1，免费、不落盘 |
| POST | `/api/barcode/export` | 登录 + `paid` 订单 | 返回 `{ pngUrl, svgUrl, metrics }`；落盘并核销 |

`metrics` 结构与预览、导出共用，前端直接显示：

```json
{
  "symbology": "EAN_13",
  "normalizedContent": "6901234567892",
  "checksumAppended": true,
  "modulePx": 4,
  "totalModules": 117,
  "xMm": 0.339,
  "magnification": 1.026,
  "widthMm": 39.6,
  "heightMm": 25.0,
  "dpi": 300,
  "warnings": []
}
```

`warnings` 用于非阻断提示，例如「放大倍率 113%，高于标准 100%，打印后比设计尺寸大 13%」。

## Risks / Trade-offs

| 风险 | 影响 | 应对 |
|---|---|---|
| 用户拿 203dpi 热敏机打小标签，`modulePx` 只有 1~2，印出来糊 | 读不出，投诉 | `modulePx < 2` 时返回警告并建议换 300dpi 或加宽标签；degraded 回验会直接挂掉这类组合 |
| 用户以为能"美化"（改颜色/加 Logo） | 期待落空 | 页面上明确一句「条形码不支持换色与叠图，会影响扫描枪识别」 |
| 店内码（20~29 开头）被误当成非法 | 一半零售用户受阻 | 只校验校验位，不限制前缀 |
| 标签尺寸与货架卡位不符 | 打出来贴不上 | UI 给常用规格预设（30×20 / 40×25 / 50×30 / 60×40mm），并显示成品实际尺寸 |
| SVG 用在印刷店时被缩放 | 条宽比例失衡 | SVG 以 mm 为单位、`viewBox` 用模块坐标，标注「请按 100% 原大输出」 |
| 与"静态码纯前端"架构不一致 | 概念负担 | 在 AGENT.md 里写清楚：条形码必须后端出图，原因是前端无 writer + 物理尺寸必须整数模块 |

## 后续（不在本次范围）

- 2D 码（DataMatrix / PDF417）：工业零件、证件、登机牌。
- ITF-14 箱码与 GS1-128 的 AI 解析。
- A4 标签纸拼版套打（真正需要它的用户目前只能一张张打）。
- 条码配色（深蓝/深绿条）——需要先验证目标扫描枪的识读阈值。
